# GDD 변경 제안

구현이 현재 기준 GDD와 다르게 간 곳을 적어 두는 문서다. 여기 있는 항목은 **아직 GDD에
반영되지 않았다.** GDD 본문은 팀 합의 뒤에 고치고, 고친 항목은 여기서 지운다.

코드와 GDD가 어긋난 채로 두지 않는다는 규칙(`CLAUDE.md`)의 예외를 만드는 문서가 아니다.
어긋난 곳이 어디인지, 왜 그렇게 했는지, GDD를 어떻게 고치자는 것인지를 한곳에 모아
합의가 끝날 때까지 놓치지 않기 위한 것이다.

## P-01. N2-M01 "두 명의 서준호" — 누가 과거이고 언제 로비에 보이는가

- 대상: GDD v5.1 §11 `N2-M01` 의 **상황**, **확인 가능한 정보 / 증거**, **선택지 및 결과**
- 구현 위치: `SeedContent.V5Mains.cs` (`BuildN2Main`), `SeedContent.Nights.cs` (`BuildLateVisitors`)
- 상태: 구현됨, GDD 미반영

### GDD가 말하는 것

> 정기 택배기사 서준호가 공동현관에 도착한다. 인터폰에는 **현재의 준호**가 보이지만
> CAM-02에는 **이미 로비에서 같은 사람이 상자를 정리하는 장면**이 잡힌다.

문 앞이 현재, 로비 카메라 속이 과거이고, 둘이 같은 순간에 보인다.

### 구현한 것

서준호는 **두 번** 호출한다.

1. **첫 번째 호출은 과거의 서준호다.** 인터폰과 현관 카메라에는 보이지만 실제 현관 앞에는
   아무도 없다. 이 시점의 로비 카메라는 빈 로비다.
2. 플레이어는 그를 들일지 정한다.
   - 들이지 않으면 아무 일도 일어나지 않는다.
   - 들이면 문이 열리고 출입 기록이 남고 **로비 카메라에 그가 잡힌다.** 실제 로비는 비어 있다.
3. **두 번째 호출이 현재의 서준호다.** 그는 처음부터 문 앞에 서 있었다.
   "아직 문을 안 열어 주셨는데요."
4. 정답은 **첫 번째는 들이지 않고, 두 번째는 로비까지** 들이는 것이다.

### 왜 바꿨는가

- GDD의 장면대로면 과거의 서준호가 **문 앞에서 허락을 기다리면서 동시에 로비 안에** 있어야
  한다. 첫 호출을 과거로 두는 한 이 둘은 같이 성립하지 않고, 플레이어는 무엇이 단서인지
  알 수 없다.
- 두 번째 호출의 대사("아직 문을 안 열어 주셨는데요")는 **앞서 문을 연 상대가 그가
  아니었을 때만** 말이 된다. 문 앞의 두 호출을 모두 현재의 서준호로 두면 방금 들어온 사람이
  문을 안 열어 줬다고 말하게 된다.
- "화면에는 들어온 사람이 실제로는 없다"는 모순이 **플레이어가 잘못 들였을 때의 결과**로만
  나타나므로, 판단과 결과가 한 줄로 이어진다.

### GDD를 이렇게 고치자는 제안

**상황**

> 비 오는 밤, 정기 택배기사 서준호가 공동현관에서 호출한다. 인터폰 화면 속 그의 뒤로는
> 비가 내리지 않는다. 그를 들이든 돌려보내든, 잠시 뒤 같은 서준호가 다시 호출한다.
> "아직 문을 안 열어 주셨는데요."

**확인 가능한 정보 / 증거**

| Invariant | 얻는 곳 | 시점 |
|---|---|---|
| 날씨: 밖은 비, 화면 속 그의 뒤는 맑음 | 첫 호출에게 질문 / 들인 뒤 CAM-02 | 판단 전 |
| 송장: 첫 호출의 송장은 2009년 양식 | 첫 호출에게 질문 | 판단 전 |
| 현관 바닥: 젖은 발자국이 없음 | 로비 현관 직접 확인 | 판단 전 |
| 시각: 로비 벽시계와 화면의 시각 표시가 다름 | 로비 직접 확인 | 판단 전 |

- 현관 유리 너머로 직접 보면 **문 앞에 아무도 없다.** 증거 항목은 아니지만 가장 직접적인 단서다.
- `N1_404_BILL_PRESERVED` 이면 첫 호출의 송장을 볼 때 "2009년 고지서와 같은 용지"라는 메모가 뜬다.
- CAM-02 의 "로비 안의 그"는 Invariant 가 아니라 **첫 호출을 들였을 때의 결과**다.

**선택지 및 결과** (첫 호출 / 두 번째 호출)

| 문 앞에서 한 일 | 결과 |
|---|---|
| 거절 / 로비까지 | 정답. `JUNHO_STATUS=TRUSTED`. Invariant 2개 이상이면 `ECHO_RULE_CONFIRMED`, SAN +3 |
| 거절 / 로비까지, 그 전에 대기시킴 | 위와 같되 `JUNHO_STATUS=NEUTRAL`, CommunityTrust -3 |
| 로비까지 / 로비까지 | 불이익 없음, 규칙 확정 없음. `JUNHO_STATUS=TRUSTED` |
| 어느 쪽이든 층 출입 | `ACCESS_DEBT +1`. 4층으로 올라가 찾아야 함 |
| (무엇이든) / 거절 | `JUNHO_STATUS=REJECTED`, `TRUST_DEBT +1`, 패키지 분실 후속 |

**HP / SAN**

- SAN -5: "불일치 장면 최초 인식"을 **두 번째 호출이 울리는 순간**으로 둔다. 첫 호출을 어떻게
  처리했든 한 번 적용된다.
- SAN -8: 층 출입을 받은 **과거의 서준호를 따라 4층에 올라갔을 때** 적용한다. 화면에는 그가
  4층에 있는데 올라가 보면 아무도 없다. (GDD의 "4F 서비스 구역"은 Night 3에 열리므로
  Night 2에서는 4층 복도다.)
- SAN +3: 정답 + Invariant 2개 이상.

### 함께 정해야 할 것

- **`N2_PACKAGE_LOST` 플래그.** §5.4 플래그 목록에 없다. "패키지 분실 후속 사건"이 읽을
  자리로 만들었다. 목록에 추가할지, 다른 이름을 쓸지.
- **ArchiveIntegrity +5 의 조건.** GDD는 "2009 상자/송장 보존"이라고만 한다. 지금은 송장
  증거를 갖고 정답 처리했을 때 준다. 2009 상자는 N2-R05 소속이다.
- **화면 속 인물이 누구인가.** 주민 데이터에 "2009년 당시 부친도 같은 구역 담당"이라는
  서준호 메모가 남아 있다. GDD는 "같은 사람"이라고 한다.
- **메인 시작 시각.** 시나리오북은 23:20, 현재 구현은 근무 초반이다.

## P-02. N4-M01 "404 주민 DB 침투" — 처리 방식과 시점

- 대상: GDD v5.1 §13 `N4-M01` 의 **선택지 및 결과**, **상태 변화**, **HP / SAN 영향**
- 구현 위치: `SeedContent.V5Mains.cs` (`BuildN4Main`), `SeedContent.cs` (`Hidden404`), `StorySequenceView.cs`
- 상태: 구현됨, GDD 미반영

GDD의 설계를 바꾼 것은 없고, GDD가 정하지 않은 부분을 구현하면서 정한 것들이다.

### 정한 것

| 항목 | GDD | 구현 |
|---|---|---|
| 처리 위치 | 선택지 4개로만 제시 | 출력·반출·삭제는 **주민 DB 화면의 404호 레코드에 있는 버튼**이다. 한 번만 할 수 있고, 아무것도 하지 않으면 "유지"다. 보고서에는 한 행동에 맞는 한 줄만 나온다 |
| 삭제 시점 | 명시 없음 | 버튼을 누르는 순간 레코드가 목록에서 사라진다. 보고는 그 뒤의 기록일 뿐이다 |
| 레코드 등장 시점 | "주민 DB 동기화 직후" (시나리오북 00:20) | 메인 사건이 시작될 때. 시각은 고정하지 않는다 |
| ChairmanAlert | +5~25 | 출력 +15, 반출 +25, 유지 +5, 삭제 +5 |
| ArchiveIntegrity | ±15 | 출력 +15, 반출 +12, 유지 0, 삭제 -15 |
| SAN -8 (이름 확인) | 시점 명시 없음 | 404호 레코드를 처음 연 순간 |
| SAN +3 (종이로 확정) | 시점 명시 없음 | 레코드를 본 뒤에 B1 종이 주민대장을 확인한 순간 |
| SAN -4 (기억 플래시) | 시점 명시 없음 | CIN-N4 와 함께. 보통은 보고 직후, `N3_HEIGHT_MATCH_NOTED` 이면 레코드를 연 순간 |
| CIN-N4 | Timeline 영상 (20~30초) | 인게임 연출. 직원증과 DB 행을 나란히 놓고 자막 4줄, 약 22초, 건너뛰기 가능. 아트 단계에서 Timeline 으로 교체 |

### 함께 정해야 할 것

- **`N4_MEMORY_OF_THE_FIRE_RESTORED` 플래그.** §5.4 목록에 없다. CIN-N4 와 SAN -4 가 한 번만 일어나게 하려고 만들었다.
- **`EV_DB404_PRINT` 증거.** "종이 출력"의 결과물로 추가했다. GDD 에는 출력본이 증거 항목으로 나오지 않는다.
- **삭제의 ChairmanAlert.** 지시를 따랐는데도 +5 인 것은, 시나리오북에서 최경태가 그날 명단의 `윤서우`를 근무자 정보와 대조하기 때문이다. 0 으로 둘지.
- **1일차의 404호 명단 노출.** 1일차에 3초간 스치는 404호 행이 예전에는 `윤하린`이라는 이름으로 보였다 (§0.16 위반). 지금은 `윤***` 로 가려진다. 1일차 담당과 확인 필요.
- **N4-R10 "선자의 증언".** 매 런 고정 등장해야 하는데 v5.1 구조로는 아직 없다. 메인의 "선자 상태에 따른 가족사진/과거 기억" 대조도 이 사건이 생긴 뒤에 붙일 수 있다.

## P-03. N6-M01 "404호는 있었습니다" 와 단일 엔딩 — 구현하면서 정한 것

- 대상: GDD v5.1 §15 `N6-M01`, §8 단일 엔딩 / Conditional Shot, §30.4·30.5 수용 기준
- 구현 위치: `SeedContent.V5Mains.cs` (`BuildN6Main`), `EndingService.cs` (`Evaluate`, `EndingShots`), `EndingViews.cs`, `WorldBuilder.cs` (`BuildUnit404Interior`), `StorySequenceView.cs` (`CIN-N6-ECHO`)
- 상태: 구현됨, GDD 미반영

v5.0의 A~D 등급 엔딩과 "살아 있는 박동식 구조"를 v5.1 계약대로 걷어냈다. 엔딩은 하나이고,
여섯 밤의 선택은 그 엔딩 안의 컷으로만 달라진다. GDD 설계를 바꾼 것은 없고 GDD가 정하지 않은
수치·시점·판정 규칙을 정했다.

### 정한 것

| 항목 | GDD | 구현 |
|---|---|---|
| 엔딩 도달 | FinalMainQuestCompleted + ExternalEvidenceSent, 생존 | 같음. N6-M01 이 해결되고 `EXTERNAL_EVIDENCE_SENT` 이면 단일 엔딩, HP 0 이면 엔딩 없음. SAN 은 어떤 값이어도 같은 엔딩 |
| 외부 전송 | 경찰 / 언론 / 주민 | 보고서의 결정 3개 (`dec_send_police/media/residents`). 셋 다 같은 엔딩이고 채널은 엔딩 안 한 컷 (`ending.shot.sent.*`) |
| 404 진입 | SAN -5, 연기 HP 위험 | 진입 순간 SAN -5. 5일차 방화문이 `OPEN` 이면 HP -10, `SAFE`·`JAMMED` 면 0 |
| 마지막 구조 ECHO | SAN -5~-8 | 시청 순간 SAN -6. 끝나는 자리에 유해가 있다는 플래그 `DONGSIK_REMAINS_FOUND` |
| CIN-N6-ECHO | Timeline 영상 | 인게임 연출. 2009/현재 대비 + 자막 5줄, 줄당 4.5초, 건너뛰기 가능. 아트 단계에서 Timeline 으로 교체 |
| 시간 부족 | "유해 수습과 원본 장부 확보가 같은 시간을 다툰다" | **먼저 한 쪽이 끝나면 다른 쪽은 사라진다** (`N6_REMAINS_LEFT_BEHIND` / `N6_LEDGER_LEFT_BEHIND`). 실시간 타이머는 두지 않았다 |
| 균형 루트 | "이전 밤 관리가 좋으면 둘 다" | 6일차 시작 시점에 `BuildingSafety ≥ 60` 이고 방화문 `SAFE` 이면 `N6_BALANCED_ROUTE`. 시작할 때 한 번만 정해진다 |
| 원본 장부 | 증거 항목 | 기존 `E19_ORIGINAL_LEDGER` 를 그대로 쓴다 (v5.0 의 `EV_ORIGINAL_LEDGER` 는 제거). ArchiveIntegrity 는 보관 핵심 증거의 기본 +10 만 오른다 |
| 둘 다 못 가져온 경우 | 위치·사진·무전 기록이 대신 나간다 | 두 목표 모두 선택이고, 아무것도 들고 나오지 않아도 전송하면 같은 엔딩. 컷은 `dongsik.located`, `ledger.digital` |
| 엔딩 연출 | Conditional Shot 영상 | 컷 문구를 순서대로 이어 붙인 텍스트. 공통 프레임 (404 탈출 → 전송 → … → 며칠 뒤 → 새벽 → 404 복원 도면) 은 항상 같다 |
| 하린 기록 | 명단 인쇄 / 서우가 손으로 적음 | 4일차 `HarinRecordPreserved` 이면 전송할 때 `END_HARIN_RECORD_FIRST_REGISTERED`. 어느 쪽이든 명단에 `윤하린` 이 나온다 |

### 걷어낸 것

- 엔딩 `ENDING_A` ~ `ENDING_D`, 등급 판정 `GradeFor`, 에필로그 수정자. 엔딩 ID 는 `SINGLE_ENDING_404_EXISTED` 와 실패 결과 `ENDING_NONE` 둘뿐이다.
- 404호 안의 살아 있는 박동식과 구조 대화 (`D_N6_DONGSIK_RESCUE` 상호작용). 6일차 어떤 결과도 `DongsikRescued` 를 세우지 않는다.

### 함께 정해야 할 것

- **SAN -6.** -5~-8 범위에서 골랐다. 앞선 밤의 누적 (캠페인 테스트 기준 N6 합계 -11) 을 보고 조정할지.
- **균형 루트 기준.** `BuildingSafety 60` 은 임의값이다. 5일차 담당 쪽 Safety 변동 폭과 맞춰 봐야 한다.
- **실시간 시간 압박.** 지금은 "순서" 로만 표현된다. 연기 타이머를 붙일지는 연출 단계에서 결정.
- **남은 문자열·업적.** `ending.ending_a..e.*`, `epilogue.*` 문자열과 등급 엔딩에 묶였던 업적 (Silence / Erased / Collapse) 이 이제 쓰이지 않는다. 지울지 다른 조건에 붙일지.
- **404호 안의 회장 대면 대화.** v5.0 그대로 남아 있다. §15 에는 없다.
- **N6-R05 고정 서브퀘스트.** v5.1 구조로는 아직 없다.
